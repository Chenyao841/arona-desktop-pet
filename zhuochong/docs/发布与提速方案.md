## 0. 本轮实测数据（先看这个，后面的结论都基于它）

### 0.1 TTS 真实耗时（本机 GPT-SoVITS，`api.py`，GPU）

| 场景 | 耗时 |
|---|---|
| 短句首次合成（冷启动后第一句） | **5.85 s** |
| 短句首次合成（稳态，5 次采样） | **1.00 / 3.24 / 1.65 s** |
| 长句首次合成（约 40 字） | **2.00 / 2.15 s** |
| 任意句子命中缓存 | **0.05 ~ 0.28 s** |

## 2. 提速优化（瓶颈在 TTS，不在"本机占用"）

### 2.1 现状拆解

```
用户发消息 → /talk（LLM，远端，1~3s）→ 前端拿到文本
                                        ↓
                          前端等首段 TTS 音频（1~3s）才显示文字+表情 ← 感知延迟的主要来源
                                        ↓
                          多句逐段串行合成（2~4 句 → 4~10s）
```

关键代码：`桌宠桌面版.html` 里 `dt.textContent = '...'` 之后要等第一段 SSE 音频到达才 `applyEffects()` + `typewriterAppend()`。

### 2.2 优化清单（按性价比排序）

> 实施状态（2026-09-12 更新）：**第 1 项已完成**；**第 2 项经核查"其实已经做了"**（见下方说明）；第 3 项改用现成的手动预热（管理页语音库 → 预热）；第 4 项待你 A/B 试听；第 6 项暂不做。

| # | 优化 | 改动量 | 预期效果 | 风险 | 状态 |
|---|---|---|---|---|---|
| **1** | **首句立即显示**：LLM 一返回就先显示文字 + 表情，音频随后跟上 | 前端小改 | **感知延迟 ≈ 减半**（4s → 2s，等于 LLM 时间） | 极低 | ✅ **已实现** |
| **2** | **TTS 并行 + 前端预取** | — | 整段耗时 4~10s → 2~3s | 中 | ✅ **核查后确认已具备**：`playSentenceFlow` 里本就有"预合成下一句"（同时发 2 个请求）；`/ai/tts/stream` 是服务端边合成边推送，与前端播放天然重叠 → **不需要再改**（避免给本地 TTS 引入并发风险） |
| **3** | **缓存命中率**：常用基础回复预热 | 无需改码 | 常见互动**近乎零等待** | 低 | ✅ 已有：管理页「语音库管理」→ **预热** 按钮（只合成未缓存的） |
| **4** | **参数调优**：`sample_steps` 32 → 16/8、主题参考音频 17s → 5~8s | 设置页可调 / 换音频 | 单句再省 0.3~1s | 中 | ⏳ 待你 A/B 试听（见 §2.3） |
| **5** | **减少无谓占用**：不用 Live2D 时切 PNG、关掉麻将轮询、IDEA 退出 | 操作层面 | 边际收益 | 低 | 按需 |
| **6** | **流式 TTS（stream_v2pro）** | 大 | 长句"等第一声" 1~3s → 0.2~0.5s | 高 | 暂不做（§2.4） |

**第 1 项实现位置（`桌宠桌面版.html`）**
- `playSpeech()`：去掉"合成期间显示 …"的等待，改为响应到达即 `showText()` + `applyEffects()`；逐段播放时不再重复追加文本
- `playSentenceFlow()` → `playBubbleTts()`：气泡开始时先把**第一句**的文字与表情打出来（`applyExpr(bubble[0]) + typewriterAppendSentence(bubble[0].text)`），该句语音到达后只补声音（`playAudio(..., skipText=true)`）；后续句仍保持"说到哪显示到哪"

### 2.3 参考音频换短会不会掉质量？（结论：不会，而且往往更稳）

- GPT-SoVITS 的参考音频是"音色 + 韵律"条件，社区经验区间是 **3~10 秒**、单人、干净、无 BGM、情绪平稳
- **过长（>15s）的坏处**：① prompt 编码更慢；② 韵律漂移（后段语调和前段不一致时，模型会学到"飘"）；③ **prompt_text 与音频必须严格一一对应** —— 长音频只要有一个字的出入，就会诱发我们之前遇到的"拉长音/吞字/复读"（`哇！` 那个 bug 就是这类）
- **换短的代价**：音色相似度基本不掉（只要同一说话人、同音质）；可能略降的是**语调丰富度**（听起来"平"一点）
- **做法建议（实测再定）**：从现有 17s 音频里裁出**前 5~8 秒最自然的一段** → 同步改 `参考音频/xxx.txt` 为**裁后音频对应的文字** → 用「语音合成调试」页做 A/B 试听同一句话（新旧参考各听 3 条）→ 满意再替换。**不要盲改**。

### 2.4 `stream_v2pro.py` 是什么？切换有什么影响？

**事实（我查了文件）**：它位于 `GPT_SoVITS/stream_v2pro.py`，是 v2Pro 的**流式推理实现**（内部类 + `test_stream()` 测试函数 + `export_prov2()` ONNX 导出），**不是 HTTP 服务**（没有 `@app.` 路由）。我们现在用的 `api.py` 是"整段合成完再一次性返回 wav"。

所以"切换"不是一个参数的事：

| 影响面 | 说明 |
|---|---|
| 服务端 | 需要**自己写一个流式服务**（WebSocket 或 chunked HTTP）把 `stream_v2pro` 包起来，或找社区现成的流式 API 实现 |
| 客户端 | 需要**边收边播**（MediaSource/WebAudio 拼接），比现在的"句级 SSE"复杂得多 |
| 收益 | 首包时间从"整句合成完"（1~3s）降到 **0.2~0.5s** 量级 → 长句体验明显提升 |
| 风险 | 分块边界可能有音质/接缝问题；与 `tts_cache`、变体机制、参考音频选择逻辑都要重新设计；调试成本高 |
| 与现状对比 | 我们**已经是句级流式**（第 1 句好后先播），而单句只有 1~3s → 真实收益有限 |

→ **我的建议**：先做 §2.2 的 1~4（改动小、收益大），流式 TTS 作为"以后想再压榨"的可选项。

## 3. 桌宠本机 vs 云端：能力拆分（**桌宠后端不上云**）

上云**不能加速桌宠**，反而会拖慢它（多一跳公网 + 依赖断链）。原因是桌宠后端有**一半能力强绑本机**：

| 能力 | 依赖 | 搬到云端 |
|---|---|---|
| 语音合成 | 本机 GPT-SoVITS `localhost:9880`（`tts_infer.yaml` 里 `device: cuda`） | **直接失效**（云端无服务/无 GPU） |
| 桌面视觉 / 麻将 / 抽卡 | `java.awt.Robot` 截屏 + 合成点击（`headless:false`） | 失效（无图形会话，且看不到你的屏幕） |
| 点击穿透锁 | Electron `127.0.0.1:3081` | 失效 |
| 网易云 | 本机 Node 服务 `localhost:3000` | 失效 |
| 对话 / 记忆 / 事件簿 / 联网查询 | 纯服务端 | ✅ 可以上云，**给 QQ 机器人用** |

**正确形态：一个代码库，两套 profile**

```
desktop profile（本机，现状）：全部能力
cloud   profile（云上/QQ 机器人）：headless=true、禁用 TTS/Robot/Electron 控制/麻将/抽卡/视觉，只用 LLM + 记忆 + 联网
```

上云改造 checklist（做 QQ 机器人时一并做）：
1. `MyBatisConfig` 里 DB 连接目前**硬编码**（root/密码写死在 Java）→ 改为读环境变量
2. `application.yml` 的 `tts.python` / `tts.api-dir` / `netease.app` 三条 Windows 绝对路径 → 按 profile 分（cloud 下关闭 autostart）
3. `spring.main.headless` 按 profile 分（cloud 用 true，并让依赖截屏的接口优雅报错）
4. 首次初始化改用 `db/schema.sql` + `db/seed.sql`（见 §6）
5. 云端时区设 `Asia/Shanghai`（否则"北京时间"注入与事件簿时间错乱）

## 4. 分发形态 A / B / C 的区别

| 维度 | **A. 本机一体化绿色包** | **B. 云大脑 + 本地壳** | **C. Docker Compose** |
|---|---|---|---|
| 发什么 | Electron 壳 + 后端 fat jar + JRE17 + 便携 MySQL + 精简素材 + 一键 bat | **只发 Electron 壳**（~150MB），配置里指向你的云后端地址 | `compose.yml`（mysql + backend 两容器）+ 壳单独装 |
| 跑在哪 | 对方电脑（离线可用） | 后端在你的云上，壳在对方电脑 | 对方电脑（需要 Docker Desktop） |
| 数据/密钥 | **对方自己的**：自己的 API Key、自己的 MySQL、自己的记忆库 | **都在你这边**：你的 API Key、你的库、你的记忆；对方的对话进你的数据库 | 对方自己的 |
| 功能完整度 | 全（Live2D + 本地 TTS + 麻将/抽卡看对方环境） | 文字 + 立绘；**没有本地 TTS**（云上无 GPU） | 全（TTS 需 GPU 直通或另跑） |
| 上手难度 | 中（要跑 MySQL、填 Key、放模型） | **最低**（解压即用） | 高（要会 Docker） |
| 体积 | 150~300MB（+可选的 JRE/Electron 运行时） | 最小（~150MB） | 镜像 ~200MB + 壳 |
| 升级维护 | 要重新打包分发 | **只改云端**，对方无感 | 换镜像 tag，最优雅 |
| 主要风险 | 对方环境各异（端口占用、MySQL 没装、路径中文） | **成本/隐私/滥用全在你**；你挂了大家都不能玩；并发高会拖垮你的 Key 额度 | Windows 上 Docker Desktop 吃资源；GPU 直通配置麻烦 |
| 适合 | 想认真体验的朋友（愿意折腾） | 给几个人试玩、演示、收集反馈 | 以后上云常驻、技术向朋友 |

**推荐路线**：先用 **B** 给朋友试玩（半天就能出，能最快拿到反馈）→ 确认有人真玩 → 再做 **A** 作为正式体验包（1~2 天）→ 将来 QQ 机器人/常驻用 **C** 的 compose 形态（与云端同构）。

三种形态都依赖同一件事：**功能默认关闭 + 设置窗口里逐个开**。这一层我们**已经建好了**（基础外观/语音 TTS/Live2D/直播/雀魂麻将/网络天才/网易云听歌/桌面视觉/联网查询 + `ai_config` 里 `live_mode`/`danmaku_enabled`/`mahjong_enabled`/`web_search_enabled`）✓ 只需要：① 种子包里开关全关、Key 留空；② 补一个"首次启动向导"（填 API Key、选要不要语音）；③ 缺依赖时给友好提示（现在 `tts.api-dir` 不存在是静默失败）。
